1.	Назначение и задачи
1.1.	Система контроля действий привилегированных пользователей (далее – Система) предназначена для управления доступом пользователей (штатные администраторы Заказчика, подрядчики и внешние пользователи) к критичным информационным ресурсам Заказчика, а также для минимизации рисков информационной безопасности, связанных с неконтролируемым доступом к таким системам;
1.2.	Система должна решать следующие основные задачи:
-	предоставление единой точки входа для привилегированных пользователей, имеющих удаленный доступ к системам Заказчика (приложения, серверы, сетевое оборудование) с возможностью персонификации доступа и разграничения прав;
-	контроль работы привилегированных пользователей, включая мониторинг сессий в режиме реального времени, а также создание записей сеансов работы;
-	автоматическое реагирование при наступлении определенных событий с помощью использования политик безопасности, списков разрешенных и запрещенных команд, а также обнаружения аномалий поведения;
-	анализ выполненных действий путем просмотра записанных сессий с использованием сквозного поиска по ним и формирование отчетности по работе привилегированных пользователей.

2.	Общие требования к Системе
2.1.	Система должна быть реализована в виде решения от одного производителя и поставляться в виде готовых программных комплексов (Virtual Appliance);
2.2.	Система должна поддерживать установку в локальной инфраструктуре без облачных компонентов;
2.3.	Система должна иметь поддержку платформ виртуализации VMware, Hyper-V, KVM, Nutanix AHV и Proxmox VE актуальных (поддерживаемых производителем) версий;
2.4.	Система не должна требовать установки агентов на рабочие станции привилегированных пользователей и целевые системы для функционирования каких-либо ее компонентов;
2.5.	Система должна работать напрямую с трафиком пользовательской сессии, без использования захвата экрана;
2.6.	В состав Системы должны входить модули по управлению доступом и управлению сессиями привилегированных пользователей; 
2.7.	Система должна иметь возможность расширения/масштабирования отдельно для каждого из модулей, добавление дополнительных модулей (узлов) должно осуществляться без остановки функционирования Системы;
2.8.	Система должна поддерживать отказоустойчивую конфигурацию (кластер) с возможностью разнесения модулей по нескольким площадкам;
2.9.	Система должна быть интегрирована в доменную инфраструктуру Заказчика и иметь способы интеграции с глобальными каталогами;
2.10.	В Системе должен быть реализован механизм автоматического обнаружения неконтролируемых привилегированных учетных записей;
2.11.	Система должна иметь встроенный движок OCR для распознавания текста в графических сессиях;
2.12.	Система должна поддерживать интеграцию со средствами многофакторной аутентификации;
2.13.	Система должна обеспечивать ведение журнала и возможности аудита всех действий, производимых пользователями и администраторами в ней;
2.14.	Обновления компонентов Системы должны осуществляться без необходимости подключения к сети Интернет;
2.15.	Заказчик обеспечивает наличие вычислительных мощностей и всего общесистемного программного обеспечения, требуемого для функционирования компонент Системы.
3.	Функциональные требования к Системе
3.1.	Система должна иметь веб-портал (на английском и русском языках), через который привилегированные пользователи будут запрашивать предоставление доступа к целевой системе без раскрытия пароля;
3.2.	В Системе должен быть реализован механизм согласования с возможностью создания кворума согласующих (например, 2 из 3 и 3 из 5);
3.3.	Система должна иметь механизм обеспечения синхронизации паролей между учетными записями различных типов (локальных аккаунтов *nix систем, доменных учетных записей Active Directory, LDAP, Баз данных Oracle, MSSQL, MySQL и т.д.);
3.4.	Система должна осуществлять автоматизацию смены паролей учетных записей и процессов запроса и согласования привилегированного доступа в многоузловом отказоустойчивом режиме, допускающем отказ одного из узлов без потери производительности и работоспособности;
3.5.	Система должна обеспечивать полностью автоматическое восстановление процессов смены паролей учетных записей и процессов запроса и согласования привилегированного доступа к целевым аккаунтам, при нарушении и последующем восстановлении сетевой связанности между узлами;
3.6.	Система должна иметь механизмы создания динамических групп целевых учетных записей и целевых систем по ряду параметров (имя, описание, платформа, тэг, доменное имя, сетевой адрес) с возможностью комбинации этих параметров и автоматического применения правил доступа к обнаруженным целевым системам и целевым учётным записям;
3.7.	Система должна обладать возможностью менять пароли привилегированных учетных записей в автоматическом режиме по заранее заданным правилам;
3.8.	Система должна иметь возможность разграничивать доступ привилегированных пользователей к целевым системам на основании определенного временного диапазона;
3.9.	Система должна иметь возможность использования подхода «четырех глаз», который позволяет предоставлять доступ к конкретной сессии только при наличии назначенного пользователя (супервайзера) и авторизации им этой сессии;
3.10.	Система должна иметь возможности предоставления аварийного доступа к целевым учетным записям с пропуском процедуры согласования и игнорирования временных интервалов разрешенного запроса доступа с оповещением ответственных сотрудников о каждом факте такого аварийного доступа;
3.11.	Система должна иметь возможность предоставлять необходимые полномочия пользователя только при запросе сессии путем помещения его учетной записи в соответствующую привилегированную группу Microsoft Active Directory (AD), и по окончании или принудительном разрыве сессии Система должна удалить пользователя из привилегированной группы AD и сменить пароль;
3.12.	Система должна иметь функциональность защиты определенного файла и предоставлять возможность запроса доступа к такому защищенному файлу;
3.13.	Сессии удаленной работы сотрудников с защищаемыми целевыми системами должны на сетевом уровне и прозрачно для конечного пользователя проходить через Систему;
3.14.	Система должна предоставлять возможность при проксировании сессий должны сохраняться все возможности контроля протокола (буфер обмена, пробрасываемые принтеры, локальные диски рабочих станций и т.д.);
3.15.	Система должна поддерживать сценарий открытия сессии к целевой системе без раскрытия пароля конечного привилегированного аккаунта;
3.16.	Система должна поддерживать возможность открытия сессии к целевой системе через любое клиентское приложение (Putty, Kitty, SecureCRT, Windows RDP client, Royal TSX на MacOS);
3.17.	Система должна предоставлять функциональность шлюза безопасности, при которой происходит аутентификация пользователя на шлюзе и его дальнейший переход к конечной привилегированной учетной записи без ввода пароля целевого аккаунта;
3.18.	Система должна позволять записывать файлы, передаваемые через SFTP, SCP или буфер обмена в RDP подключениях с возможностью восстановления их в исходном виде;
3.19.	Система должна обеспечивать мониторинг и регистрацию действий пользователей при совершении ими манипуляций на целевых системах:
-	поток пользовательского ввода/вывода;
-	метаданные (учетная запись пользователя, временные метки, запускаемые процессы, заголовки открываемых окон, имена передаваемых файлов).
3.20.	Система должна обеспечивать контроль привилегированных пользователей, которые подключаются к целевым системам как минимум по следующим протоколам:
-	Citrix ICA (в т.ч. инкапсулированный в CGP) включая поддержку записи последних серверных версий Citrix – XenApp 6.5, XenDesktop 7.0, 7.6 и 7.15, SOCKS proxy и Citrix STA;
-	RDP (в т.ч. over TLS) версий 4,5,6,7,8,8.1, в т.ч. Remote Desktop Services (RemoteApp);
-	X11 (over SSH);
-	VNC (в т.ч. over SSL);
-	SSH, в том числе контроль и запись трафика Local и Remote Port Forwarding;
-	Telnet, TN3270;
-	SFTP (SCP);
-	HTTP и HTTPS;
-	Microsoft SQL Server версии 2014 и выше.
3.21.	Система должна обеспечить возможность контроля и мониторинга приложений, публикуемых посредством терминальных служб Microsoft RDS;
3.22.	Система должна обеспечить поддержку GSSAPI и Kerberos в SSH сессиях;
3.23.	Система должна предоставлять возможность просмотра активной сессии в режиме реального времени с возможностью ее прерывания. Просмотр активной сессии должен производиться с помощью проприетарного защищенного проигрывателя;
3.24.	Система должна предоставлять возможность выгрузки из защищенного проигрывателя должна быть возможность экспорта в формате PCAP;
3.25.	Система должна обеспечить просмотр завершенной сессии с возможностью текстового поиска, также вести сквозной поиск одновременно по всему объему записанных сессий, включая расположенные в архиве, а также иметь возможность задания множества поисковых критериев одновременно:
-	время начала и завершения сессии;
-	IP-адрес (подсеть) пользователя;
-	IP-адрес (подсеть) сервера, с которым была установлена сессия;
-	протокол (список протоколов), по которому была установлена сессия;
-	часть слова или фраза в потоке пользовательского ввода/вывода (должен быть реализован полнотекстовый поиск по потоку пользовательского ввода/вывода);
-	метаданным (учетная запись пользователя, временные метки, запускаемые процессы, заголовки открываемых окон, имена передаваемых файлов);
-	часть имени файла, переданного во время сессии.
3.26.	Система должна предоставлять возможность ускорять и замедлять скорость воспроизведения записи;
3.27.	Запись сессии должна включать полный список команд, выполненных пользователем во время записи, и не должна требовать установки агентского программного обеспечения;
3.28.	Запись сессий должна осуществляться из потока ввода/вывода (upstream/downstream) без потери качества и требовать минимальный объем на системе хранения, при этом прямая запись в формате видеофайлов или снимков экрана не допускается;
3.29.	Система должна предоставлять возможность экспорта записанной сессии в файл для воспроизведения ее как видео;
3.30.	Система должна обеспечить возможность уполномоченному оператору разорвать любую активную (незавершенную) сессию; 
3.31.	Система должна поддерживать возможность автоматического разрыва сессии при нарушении политики безопасности (в том числе на основе черных и белых списков команд/заголовков окон); 
3.32.	Система должна иметь возможность массовой загрузки черных и белых списков;
3.33.	Записанные сессии должны содержать следующую информацию:
-	перехваченный сетевой трафик поддерживаемого протокола;
-	текст, введенный пользователем и отображенный пользователю (поток пользовательского ввода/вывода); должны поддерживаться распространенные кодировки символов русского языка, в том числе: CP1251, KOI8-R, UTF-8;
-	общая информация о сессии (метаданные), в том числе: время начала и завершения сессии, имена переданных во время сессии файлов, разрешенные и запрещенные подканалы протоколов от пользователя к серверу, список выполненных команд в гипертекстовых протоколах.
3.34.	Система должна обеспечить возможность сохранить переданные во время сессии SFTP, SCP или RDP файлы (в том числе бинарные) в оригинальном виде, с возможностью восстановления в случае удаления;
3.35.	Система должна обеспечить поддержку хранения записанных сессий с защитой от несанкционированного доступа;
3.36.	Система должна обеспечить возможность организации автоматической архивации файлов с записанными сессиями в сетевое хранилище Заказчика по протоколам SMB/CIFS версии 2, 3, 4, а также по сетевому протоколу NFS;
3.37.	Система должна иметь возможность разграничения доступа администраторов с возможностью ограничения доступа к потоку пользовательского ввода, на просмотр завершенных и активных сессий пользователей. Подключение стороннего администратора для перехвата управления в сессия не допускается;
3.38.	Система должна иметь механизмы централизованной аутентификации администраторов для доступа к веб-консоли с помощью Microsoft AD, протокола Radius или сертификатов x509.
3.39.	Система должна иметь функционал выявления нетипичного поведения пользователей при работе под привилегированными учетными записями и формирования индивидуальных индексов риска для таких пользователей;
3.40.	Система должна при выявлении нетипичного поведения пользователей учитывать отклонения по времени входа, диапазону серверов и приложений, аномалии по набору производимых активностей, динамике нажатия клавиш при вводе информации, а также движения мыши;
3.41.	Система должна иметь функционал уведомления заинтересованных лиц в случае выявления нетипичного поведения пользователей в сессии.
4.	Требования к лицензированию
4.1.	Система должна лицензироваться по модели ежегодной подписки; 
4.2.	Предлагаемые лицензии Системы должны включать в себя техническую поддержку и подписку лицензий от Производителя со сроком действия на один год с даты активации;
4.3.	Предлагаемые лицензии Системы должны обеспечивать доступ для не менее чем 310 единиц оборудования;
4.4.	Предлагаемые лицензии Системы должны обеспечивать подключение к неограниченному количеству целевых систем;
4.5.	Предлагаемые лицензии Системы должны включать в себя возможность развертывания неограниченного количества узлов Системы, включая построение отказоустойчивых кластеров;

5.	Требования к сопутствующим услугам
5.1.	Поставщик должен выполнить следующие услуги по предоставлению лицензий к Системе и настройке Системы: 
5.1.1.	Установка, активация и настройка функционала всех компонент Системы; 
5.1.2.	Настройка целевых систем, не более 3 экземпляров каждого типа; 
5.1.3.	Настройка ролей и доступов для различных групп пользователей; 
5.1.4.	Настройка отчетов
5.2.	Проведение интеграции с согласованным списком ИТ сервисов – служба каталогов и сервисом электронной почты, и т.д.;
5.3.	Обучение специалистов Заказчика, не менее двух человек, администрированию Системы;
5.4.	Предоставление комплекта технической и эксплуатационной документации в электронном виде (Руководство Администратора, Паспорт Системы).
