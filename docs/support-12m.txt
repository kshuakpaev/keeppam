# KeepPAM: техническая поддержка 12 месяцев (SOW-SUPPORT-12M)

Коммерческий модуль **без изменений кода**. Оформляет обязательство производителя по T-54 (`docs/main22.txt`) и связку с лицензией T-52/T-53 (`docs/license.txt`, `docs/kp.txt` уровень C).

Использовать как **черновик приложения к контракту** и внутренний runbook команды сопровождения.

---

## 1. Что входит в SOW (типовой пакет)

| Включено | Не включено (отдельный SOW / доп. оплата) |
|----------|---------------------------------------------|
| Консультации по эксплуатации KeepPAM on-prem | Новые модули уровня C (`docs/sow-backlog.txt`) |
| Разбор инцидентов на стенде заказчика | Citrix HDX OEM, geo-HA второго ЦОД «под ключ» |
| Багфиксы в рамках поставленной версии | Кастомная разработка вне scope пилота |
| Помощь с upgrade/patch (offline pack) | 24×7 on-site без отдельного SLA |
| Рекомендации по HA, backup, SIEM, LDAP | Поддержка ПО третьих сторон (AD, Citrix, z/OS) |
| Безлимит **пользователей** портала | Сверхлимит **активов** сверх `max_assets` в license |

**Лицензия активов:** cap по `license.json` (`max_assets`, soft warn, hard block) — см. `docs/license.txt`. Пользователи портала не лимитируются entitlement-файлом.

**Срок:** 12 календарных месяцев с даты **акта ввода в промышленную эксплуатацию** (или иной даты, зафиксированной в контракте).

---

## 2. Действия до старта поддержки (поставка)

Чек-лист исполнителя **до** начала 12-месячного периода:

1. **Приёмка пилота A** по `docs/kp-acceptance.txt` (или согласованный subset) — подписанный акт.
2. **Выдать license.json** заказчику: `customer`, `max_assets` (≥100 для T-52), `expires` = дата окончания entitlement (если нужен срок лицензии отдельно от поддержки).
3. **Зафиксировать baseline версии:** git tag / digest образов, `deploy/compose*.yml`, миграции БД на момент приёмки.
4. **Передать комплект документов:**
   - `docs/install.txt`, `docs/prod-infra.txt`, `docs/geo-ha.txt` (если HA),
   - `docs/kp-acceptance.txt`, `docs/demo-45min.txt`,
   - контакты эскалации (см. §5).
5. **Обучение** (минимум): 1 сессия для админов ИБ (2–4 ч) — JIT, vault, forensic, backup/restore метаданных.
6. **Канал тикетов:** email + опционально портал; указать язык (RU/EN) и рабочие часы.
7. **NDA / доступ:** VPN или jump для P3+; политика логов/recordings на стенде заказчика.

## 3. Регламент в период поддержки (12 мес)

### 3.1 Классы обращений (пример)

| Класс | Примеры | Целевое время **реакции** (8×5)* | Целевое **решение** |
|-------|---------|----------------------------------|---------------------|
| **P1** | Портал недоступен; массовый отказ сессий; data loss | 4 ч | 1 раб. день |
| **P2** | Один протокол/шлюз; JIT/rotate не работает; SIEM stop | 1 раб. день | 3 раб. дня |
| **P3** | UI/отчёт; некритичный баг; вопрос по настройке | 2 раб. дня | 10 раб. дней |
| **P4** | Консультация, «как сделать», roadmap | 3 раб. дня | по договорённости |

\*8×5 — пн–пт, 10:00–18:00 MSK (или часовой пояс заказчика в контракте). **24×7** — только отдельным доп. SOW.

### 3.2 Типовые действия по типу тикета

**Инцидент (P1–P2)**

1. Подтвердить приём, назначить инженера, запросить: версия, `GET /readyz`, логи API/worker, последние изменения.
2. Воспроизвести на lab при возможности (`make acceptance-smoke`, `docs/kp-acceptance-lab.txt`).
3. Workaround для заказчика (откат конфига, drain worker, disable политики) — если fix не в тот же день.
4. Patch/minor release или hotfix-образ; инструкция offline update (`docs/offline-update.txt` если есть, иначе compose pull + migrate).
5. Post-mortem одностраничный для P1 (причина, действия, prevention).

**Запрос на изменение / консультация (P3–P4)**

1. Ответ со ссылкой на `docs/*.txt` или конфиг UI.
2. Если требуется код — перевести в коммерческую оценку (новый SOW-id), **не** включать в SUPPORT-12M.

**Плановое обслуживание**

| Периодичность | Действие |
|---------------|----------|
| Ежеквартально | Напоминание о backup PG/recordings; проверка `expires` license; advisory по CVE базового образа |
| При release | Release notes + рекомендация upgrade; окно согласовать с заказчиком |
| По запросу | Review `license.json`, HA drill (failover worker), smoke после upgrade |

## 4. Что запрашивать у заказчика в тикете

Минимальный пакет для ускорения разбора:

```
- ID тикета / контакт дежурного
- Класс P1–P4
- Версия KeepPAM (image tag / git commit из UI About или deploy)
- Симптом и время начала (UTC+…)
- Затронутые протоколы (SSH/RDP/…)
- Фрагмент логов: api, session-worker (без секретов/vault)
- Изменения за 24 ч (LDAP, firewall, upgrade)
- Для P1: результат curl /readyz, статус postgres/redis
```

**Не запрашивать** пароли vault, wire_token, содержимое recordings без явного DPA и минимизации.

## 5. Эскалация (пример)

| Уровень | Кто | Когда |
|---------|-----|-------|
| L1 | Support engineer | Все входящие |
| L2 | Backend/infra инженер KeepPAM | P2+, нет решения 1 раб. день |
| L3 | Tech lead / architect | P1, data integrity, security |
| Заказчик | Владелец актива / CISO | Коммуникация статуса P1 каждые 4 ч |

Контакты заполняются в контракте (email, телефон, Telegram по согласованию).

---

## 6. Границы ответственности

**Исполнитель отвечает за:**

- работоспособность компонентов KeepPAM в scope поставки (API, worker, guacd bundle, шлюзы wire);
- дефекты документированного поведения текущей версии;
- инструкции по восстановлению метаданных из backup.

**Заказчик отвечает за:**

- инфраструктуру (VM, сеть, DNS, TLS-сертификаты, AD/LDAP);
- backup/restore исполнение на площадке;
- лимит активов и соблюдение license;
- целевые ОС и клиенты (x3270, mstsc, браузер).

**Явно out of scope SUPPORT-12M:**

- SOW-модули, не заключённые в контракт;
- производительность Citrix/z/OS «как у Fudo» без SOW-CITRIX-HDX / TN3270-DBCS;
- pentest и аттестация ФСТЭК (отдельные работы).

## 7. Завершение и продление

**За 60 дней до окончания 12 мес:**

1. Отчёт: количество тикетов по классам, выполненные upgrade, открытые known issues.
2. Предложение продления (SOW-SUPPORT-12M renewal) или переход на T&M.

**В последний день периода:**

- Поддержка **консультаций по новым тикетам** прекращается, если не продлено.
- **Критичные P1** на уже открытых тикетах — довести до workaround или fix по доброй воле (лучше прописать в контракте явно).

## 8. Acceptance (DoD модуля SOW-SUPPORT-12M)

Не `make test`, а **документы и процесс**:

- [ ] Подписан контракт / приложение с классами P1–P4 и часами реакции
- [ ] Переданы license.json, baseline версии, контакты эскалации
- [ ] Проведено обучение админов (протокол или запись)
- [ ] Принят минимум один учебный тикет P4 (проверка канала)
- [ ] В реестре SOW статус «активен» с датами start/end
