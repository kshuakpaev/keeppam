# 2. Контроль ОС

Здесь KeepPAM уже становится значительно интереснее обычного bastion host.

### SSH

Контролировать:

* login;
* logout;
* команды;
* `sudo`;
* `su`;
* SCP;
* SFTP;
* port forwarding;
* X11 forwarding;
* SSH tunneling.

Например:

```text
User: ivan
Target: prod-linux-01

ALLOW:
    systemctl status nginx
    systemctl restart nginx
    journalctl -u nginx

DENY:
    useradd
    passwd
    rm -rf
    iptables
```

### Важный момент

Я бы разделил:

**Session Access**

и

**Command Access**

То есть:

```text
Иван может войти на сервер
        ↓
но не имеет права выполнять
определённые команды
```

Это гораздо более мощная модель.

# 4. Контроль БД

С учётом того, что мы уже обсуждали PostgreSQL/MySQL, я бы сделал **три уровня**.

### Level 1 — Database Session

```text
User
 ↓
KeepPAM
 ↓
PostgreSQL
```

Контроль:

* кто подключился;
* к какой БД;
* какой пользователь БД;
* время;
* IP;
* длительность.

### Level 2 — SQL Audit

Записываем:

```sql
SELECT ...
INSERT ...
UPDATE ...
DELETE ...
CREATE ...
ALTER ...
DROP ...
```

И связываем SQL с пользователем PAM:

```text
PAM User
    ↓
PAM Session
    ↓
DB Account
    ↓
SQL Query
```

### Level 3 — SQL Policy

Например:

```text
SELECT       ALLOW
INSERT       ALLOW
UPDATE       APPROVAL
DELETE       DENY
DROP         DENY
ALTER        DENY
```

А дальше можно идти ещё глубже:

```text
Database
   ↓
Schema
   ↓
Table
   ↓
Column
   ↓
Operation
```

Например:

> Иван может `SELECT` из `users`, но не может читать `password_hash`.

Это уже очень сильный функционал.

# 7. Network PAM

Отдельный класс контроля.

Политика:

```text
USER
 ↓
SOURCE
 ↓
TARGET
 ↓
PORT
 ↓
PROTOCOL
```

Например:

```text
Ivan
→ 10.10.20.15
→ TCP/22
→ ALLOW
```

Но:

```text
Ivan
→ 10.10.20.15
→ TCP/5432
→ DENY
```

При этом другой пользователь:

```text
DBA
→ 10.10.20.15
→ TCP/5432
→ ALLOW
```

# 8. JIT — Just-In-Time Access

Очень рекомендую включить в архитектуру с самого начала.

Не:

```text
Ivan → permanent → root
```

а:

```text
Ivan
 ↓
Request
 ↓
Approval
 ↓
root
 ↓
30 minutes
 ↓
automatic revoke
```

Например:

> Доступ к production PostgreSQL на 45 минут.

После 45 минут доступ автоматически исчезает.

---

# 9. JEA — Just Enough Administration

Ещё лучше.

Не выдавать:

```text
root
```

а выдавать:

```text
restart nginx
view logs
check status
```

То есть пользователь получает **минимально необходимую привилегию**.

# 10. Secret Management

KeepPAM должен хранить:

```text
Passwords
SSH Keys
API Keys
Tokens
Certificates
Service Accounts
```

Но пользователь **не должен видеть секрет**.

Например:

```text
Ivan
 ↓
Request SSH
 ↓
KeepPAM
 ↓
получает credential из Vault
 ↓
SSH → Server
```

Пароль Иван никогда не увидел.

После использования:

```text
Session END
 ↓
Credential rotation
```

# 14. Context-Based Access

Политика может учитывать:

```text
USER
ROLE
TARGET
TIME
IP
DEVICE
LOCATION
PROTOCOL
COMMAND
RISK
TICKET
```

Например:

```text
IF
    user.role = DBA
AND
    target.environment = PROD
AND
    time BETWEEN 09:00-18:00
AND
    source.network = CORPORATE
AND
    MFA = true

THEN
    ALLOW
```

А ночью:

```text

    REQUIRE_APPROVAL
```

# 15. Risk Engine

Все факторы можно свести в:

```text
Risk Score
```

Например:

```text
User risk             10
Unknown device        20
Outside office        15
Night time            20
Production             30
DROP TABLE             50
-------------------------
TOTAL                 145
```

Политика:

```text
0–30     ALLOW
31–60    AUDIT
61–90    MFA
91–120   APPROVAL
121+     DENY
```

* кто имел доступ;
* кто получил privileged access;
* кто согласовал;
* кто подключался;
* какие команды выполнялись;

# 20. Я бы построил KeepPAM вот таким образом

```text
                         KeepPAM
                            │
        ┌───────────────────┼───────────────────┐
        │                   │                   │
     IDENTITY            POLICY             VAULT
        │                   │                   │
    Users/Roles         RBAC/ABAC          Passwords
    MFA                 JIT                SSH Keys
    Groups              JEA                Tokens
        │                   │
        └──────────────┬────┘
                       ↓
                 ACCESS ENGINE
                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
     SSH/RDP           DB              APP/API
       │               │                │
    Commands          SQL             HTTP/API
       │               │                │
       └───────────────┼────────────────┘
                       ↓
                  SESSION ENGINE
                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
    Recording         Audit             DLP
                       │
                       ↓
                  RISK ENGINE
                       │
                       ↓
                SIEM / Analytics
```

### А самое главное

Я бы **не делал отдельную систему правил для SSH, отдельную для DB и отдельную для HTTP**.

Лучше сделать единый объект:

**Policy**

```text
WHO
WHAT
WHERE
WHEN
FROM WHERE
HOW
CONTEXT
ACTION
```

И уже протокол становится транспортом.

То есть одна политика может выглядеть концептуально так:

```text
User:        DBA_Group
Target:      PROD-POSTGRES
Protocol:    PostgreSQL
Database:    accounting
Schema:      public
Operation:   SELECT
Time:        09:00-18:00
Source:      Corporate Network
MFA:         Required
Approval:    Not required
Recording:   Yes
DLP:         Yes
Action:      ALLOW
```

А другая:

```text
User:        DBA_Group
Target:      PROD-POSTGRES
Operation:   DROP
Time:        Any
Approval:    Required
MFA:         Required
Recording:   Yes
Action:      APPROVAL
```

**Именно такой Policy Engine я бы считал центральным компонентом KeepPAM.** Тогда SSH, RDP, PostgreSQL, MySQL, HTTP/API и будущие протоколы становятся подключаемыми enforcement points, а не отдельными PAM-системами.
